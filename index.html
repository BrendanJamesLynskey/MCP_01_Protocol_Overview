01

The M×N Problem — Why MCP Exists

By late 2024 every serious LLM application had reinvented the same wheel: a bespoke way to plug a model into a database, a filesystem, a ticketing system, an internal API. M AI applications times N data sources is M×N integrations — each one a brittle bag of function-calling JSON, prompt scaffolding, and authentication glue.

Anthropic open-sourced the Model Context Protocol in November 2024 to collapse this to M+N: each application speaks one protocol, each tool ships one server. The marketing line is “USB-C for AI” — a single shaped plug that any compliant host can talk to.

Before MCP — M×N integrations

Every host wrote its own connector for every tool. Cursor + Postgres, Claude Desktop + Postgres, Continue + Postgres, … same job, three implementations, three sets of bugs.

With MCP — M+N integrations

The Postgres team writes one server. Every compliant host gets it for free. The work moves from N-app-teams to one tool-team.

Why it stuck

MCP is small enough to read in an afternoon, JSON-RPC over a stream that any language can speak, and it ships with reference SDKs in Python, TypeScript, Java, C#, Kotlin, Swift, Go and Ruby. The barrier to writing a server is “define a function and a JSON Schema”.

02

Host / Client / Server — The Three Roles

The MCP architecture has three named participants. Mixing them up is the single most common source of confusion when reading the spec, so it's worth pinning down up front:

RoleWho plays itJob
HostClaude Desktop, Claude Code, Cursor, Zed, Continue, VS Code, your own agent runtimeOwns the LLM. Orchestrates the conversation. Decides which servers to load.
ClientA library inside the host — one client instance per connected serverSpeaks the JSON-RPC protocol. 1:1 with a server. Stateful.
ServerThe Postgres server, the GitHub server, your own internal data serverExposes tools, resources, prompts. Knows nothing about the LLM. Pure protocol citizen.
Mental model

Think of the host as the operating-system shell, the clients as file descriptors, and the servers as long-running daemons. The host is where trust lives; the servers are dumb actuators that the host has chosen to load.

03

JSON-RPC 2.0 — The Wire Alphabet

MCP doesn't invent a new wire format. Every message is a JSON-RPC 2.0 envelope, defined by the 5-page spec from 2010. There are exactly three message shapes:

Request

Has an id. Expects a response. {"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}

Response

Carries the same id. Either result or error, never both. {"jsonrpc":"2.0","id":1,"result":{...}}

Notification

Has no id. Fire-and-forget. {"jsonrpc":"2.0","method":"notifications/initialized"}

The Standard Error Codes

JSON-RPC defines reserved codes; MCP layers a small set on top. Anything outside -32768..-32000 is yours to define for tool-level failures.

CodeNameWhen
-32700Parse errorThe JSON itself was malformed
-32600Invalid requestNot a valid JSON-RPC envelope
-32601Method not foundThe method name is unknown
-32602Invalid paramsThe params didn't match the schema
-32603Internal errorCatch-all for server bugs
-32002Resource not foundMCP-specific (resources/read on a missing URI)
Important: tool errors are NOT JSON-RPC errors

If a tool runs and the operation fails (e.g. create_issue hit a 401), the JSON-RPC call still succeeds with a result. The tool result carries isError: true and the failure message. JSON-RPC errors are reserved for protocol-level problems — bad params, missing methods, unmarshalable JSON. Mixing the two is the bug every new server author writes once.

04

The Five Primitives

The protocol's surface area is small: three primitives a server can offer, two that a client can offer back. Everything else in MCP is plumbing for these.

Server-side primitives (server → client)

Tools

Side-effecting functions the model can call. tools/list, tools/call. Each tool ships a JSON Schema for its arguments and (since 2025-06-18) for its structured output. Annotations declare read-only / destructive / open-world.

Resources

Read-only data identified by URI. resources/list, resources/read, resources/subscribe. Subscriptions push resources/updated notifications — how a server tells the client “the file you were watching changed”.

Prompts

Reusable, parameterised templates the user can invoke explicitly — typically as slash commands or quick actions. prompts/list, prompts/get. Different from a tool: a prompt is composed and shown to the user, a tool is executed.

Client-side primitives (client → server)

Sampling

sampling/createMessage. The server asks the client to call its LLM. Lets a server build agentic behaviour without bringing its own model. The host MUST gate this with explicit user approval.

Elicitation

elicitation/create, standardised in 2025-06-18. The server presents a typed, schema-constrained question (“destination zip code?”) and the client renders a form. Returns accept, decline, or cancel.

Two more first-class concepts

Roots are URIs the host has authorised the server to touch (e.g. a project directory). roots/list is a client-side request.

Logging is the notifications/message stream and logging/setLevel request — the server can emit structured log records to the client at standard syslog levels.

05

Capability Negotiation

MCP explicitly avoids feature-detection by trial-and-error. At handshake time both sides exchange a capabilities object; nothing else can be assumed. This is what lets a Python server written against the 2024-11-05 spec keep working with a Claude Desktop running 2025-06-18.

Server → client (initialize result, abridged)
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "tools":     { "listChanged": true },
      "resources": { "subscribe":   true,
                       "listChanged": true },
      "prompts":   { "listChanged": true },
      "logging":   {},
      "completions": {}                // argument autocompletion
    },
    "serverInfo": { "name": "my-server", "version": "0.4.1" },
    "instructions": "Use the ‘query’ tool to read the database."
  }
}
Read this carefully

An empty object ("logging": {}) means “I support this primitive but with no sub-options”. An absent key means “I do not support this primitive”. The client MUST NOT call logging/setLevel on a server that didn't declare logging. Calling an undeclared primitive returns -32601 Method not found.

Sub-flags worth knowing

FlagMeaning
tools.listChangedServer may emit notifications/tools/list_changed when its tool catalogue changes at runtime
resources.subscribeServer supports resources/subscribe — per-URI change watching
resources.listChangedServer may emit a global resources-changed notification (catalogue-level)
sampling (client side)Client has an LLM available and will service sampling/createMessage
elicitation (client side)Client can render schema-constrained user prompts
roots.listChangedClient will tell the server when the root list changes (e.g. user opened a new project)
06

Lifecycle — initialize → operate → shutdown

Every MCP session goes through the same three phases. The protocol is strict about ordering: a request issued in the wrong phase is a protocol error.

Protocol-version negotiation

The client proposes a version. The server picks one it supports (typically the highest mutually-supported value) and returns it in the initialize result. From 2025-06-18 onward the agreed version MUST also be sent on every subsequent HTTP request as MCP-Protocol-Version: 2025-06-18 — this is what catches misconfigured proxies and stale clients.

07

Versioning — The Spec Timeline

MCP versions are date-stamped, not semver. The string is literally the date the spec was frozen. Three versions matter as of 2026:

VersionHeadlineWhat changed
2024-11-05Initial releaseOpen-sourced by Anthropic. JSON-RPC + stdio + HTTP/SSE. Tools, resources, prompts, sampling, roots, logging.
2025-03-26Streamable HTTP & authNew Streamable HTTP transport (HTTP+SSE deprecated). OAuth 2.1 normative. Audio content type. Tool annotations (read-only/destructive/etc).
2025-06-18Current production targetJSON-RPC batching removed. Elicitation standardised. Structured tool output (separate structuredContent). Resource links in tool results. Mandatory MCP-Protocol-Version header. OAuth resource server clarifications (RFC 8707 audience binding).

Why dates, not semver?

Date-stamping makes the spec trivially comparable (string sort ≡ chronological order) and dodges the semver fight over what counts as “breaking”. The compatibility contract is: servers SHOULD support a window of recent versions; clients negotiate the highest both sides know.

Migration footguns to remember

Batched JSON-RPC died. If you have a 2024-11-05 server happily returning [{...}, {...}], a 2025-06-18 client will refuse it. The reasoning was that batching never composed cleanly with SSE streams and almost no SDKs implemented it correctly.

HTTP+SSE is deprecated, not removed. Existing servers keep working; new ones SHOULD use Streamable HTTP. Deck 02 covers the wire-level differences.

Worked Example — A Full Annotated Exchange

End-to-end: a Claude Desktop client connects to a tiny weather server, lists tools, calls one, receives a structured result. Every line on the wire is shown.

1. initialize (client → server, request)
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
  "protocolVersion":"2025-06-18",
  "capabilities":{
    "sampling":{},
    "elicitation":{},
    "roots":{"listChanged":true}
  },
  "clientInfo":{"name":"claude-desktop","version":"0.13.0"}
}}
2. initialize result (server → client, response)
{"jsonrpc":"2.0","id":1,"result":{
  "protocolVersion":"2025-06-18",
  "capabilities":{
    "tools":{"listChanged":true},
    "resources":{"subscribe":false,"listChanged":true}
  },
  "serverInfo":{"name":"weather-server","version":"1.2.0"},
  "instructions":"Provide forecasts via the ‘forecast’ tool. Locations must be ISO 3166-2 codes."
}}
3. notifications/initialized (client → server, notification — no id)
{"jsonrpc":"2.0","method":"notifications/initialized"}
4. tools/list (request / response)
// → client
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
// ← server
{"jsonrpc":"2.0","id":2,"result":{
  "tools":[{
    "name":"forecast",
    "title":"Weather Forecast",
    "description":"Return a 24-hour forecast for an ISO 3166-2 region.",
    "inputSchema":{
      "type":"object",
      "properties":{ "region":{"type":"string","pattern":"^[A-Z]{2}-[A-Z0-9]{1,3}$"} },
      "required":["region"]
    },
    "outputSchema":{
      "type":"object",
      "properties":{
        "tempC":{"type":"number"},
        "windKph":{"type":"number"},
        "summary":{"type":"string"}
      },
      "required":["tempC","windKph","summary"]
    },
    "annotations":{ "readOnlyHint":true, "openWorldHint":false }
  }]
}}
5. tools/call (request / response, with structured output)
// → client
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{
  "name":"forecast",
  "arguments":{"region":"GB-LND"}
}}
// ← server
{"jsonrpc":"2.0","id":3,"result":{
  "content":[{"type":"text","text":"London: 12°C, 14 km/h, light rain easing this evening."}],
  "structuredContent":{"tempC":12.0,"windKph":14.0,"summary":"light rain easing"},
  "isError":false
}}
What ‘structured output’ gives you

The model still sees the human-readable content — that's what gets concatenated into the LLM's context. The structuredContent is for downstream code: a workflow engine that wants to branch on tempC doesn't have to regex it out of the prose. Validation against outputSchema is the host's responsibility — but if the schema is published, both sides can rely on it.

09

What to Take Away

  • MCP is JSON-RPC 2.0 with five primitives bolted on. The whole protocol is small enough to keep in your head.
  • Three roles, three nouns. Host owns the LLM. Client is one-per-server inside the host. Server is a pure protocol citizen with no model awareness.
  • Three message shapes. Request/response carry an id; notifications don't. Tool failures live in result.isError, not in JSON-RPC errors.
  • Five primitives. Server exposes tools, resources, prompts. Client exposes sampling, elicitation. Roots and logging are first-class auxiliaries.
  • Capabilities are negotiated up front. Absent ≠ empty. Don't probe; check the initialize result.
  • Versions are date-stamps. Pin to the highest common one. 2025-06-18 is the current target; expect another bump every few months.
